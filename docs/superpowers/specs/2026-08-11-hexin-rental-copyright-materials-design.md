# 和信租通用化软著申报材料设计规范

## 1. 目标与批准口径

本设计按用户批准的“方案 A（严格申报版）”执行，为三个通用化题目逐套生成可编辑的 Markdown 申报材料，并以 PDF 渲染结果证明页数、字号、A4 页面和逐页行数满足仓库规则。

每套材料包含两个主体文档：

1. `01-程序鉴别材料.md`：恰好 60 页，每页至少 50 个非空有效代码行；正文只能来自已审计的真实仓库代码。
2. `02-软件说明书.md`：恰好 60 页，每页至少 30 个非空正文行；内容必须与该题目的真实页面、接口、状态和操作流程对应。

另行提供登记信息、运行环境、代码来源、规格核对和材料索引。Markdown 是交付源文件；PDF 是分页和版式验收证据，不替代 Markdown。

## 2. 题目、顺序与代码边界

按以下顺序逐套生成：

| 顺序 | 目录 ID | 软件名称 | 已分配文件 | 有效行 | 建议完成日期依据 |
|---|---|---|---:|---:|---|
| 1 | `01-channel-identity-verification` | 渠道推广与身份核验管理系统 V1.0 | 21 | 4,838 | 入选代码最新行时间 2025-11-29 |
| 2 | `02-mobile-role-collaboration` | 移动端多角色业务协同管理系统 V1.0 | 12 | 3,968 | 入选代码最新行时间 2026-01-05 |
| 3 | `03-electronic-agreement-compliance` | 电子协议展示与合规授权管理系统 V1.0 | 25 | 4,334 | 入选代码最新行时间 2025-12-23 |

代码边界以 `copyright/analysis/hexin-rental/candidate-code-audit.csv` 中 `allocation_status=allocated` 的记录为唯一入口。生成器必须同时验证：

- 每个记录的 `date_status` 为 `strict_eligible`；
- 每个记录的 `prior_overlap_status` 为 `clear`；
- 文件内容 SHA-256 与清单一致；
- 三套材料之间不存在重复内容哈希；
- 不读取 `rental-platform-backend`、`rental-platform-admin`、`rental-platform-app`；
- 不读取 `node_modules`、`uni_modules`、`dist`、`build`、`target`、`vendor` 或未提交工作树内容。

登记信息中的开发完成日期只是基于代码证据形成的建议值，提交前由申请人确认。申请人名称、证件信息、权利取得方式等主体信息没有证据时必须明确写为“未提供，提交前由申请人确认”，不得编造。

## 4. 程序鉴别材料设计

### 4.1 代码流构建

生成器按题目、仓库名、相对路径稳定排序，从清单记录的 Git HEAD 提交对象读取文件，不读取工作树。文件内容按原有行序串联为完整代码流，空行不计入有效行；不插入 `// File:`、省略标记、解释文字、占位代码或行号。

`SOURCE_MANIFEST.json` 独立记录每个源文件的仓库、提交、相对路径、SHA-256、有效行数和在完整代码流中的区间。文件边界证据放在清单中，不污染程序正文。

### 4.2 前 30 页和后 30 页

每个题目的完整代码流均超过 3,000 个有效行。程序材料选取：

- 第 1 至 30 页：完整代码流的连续前 1,500 个有效行；
- 第 31 至 60 页：完整代码流的连续后 1,500 个有效行；
- 每页固定 50 个有效代码行；
- 若前后片段重叠、总有效行不足 3,000、哈希不一致或文件无法从 Git 对象读取，生成立即失败。

Markdown 使用明确的 60 个页面容器。页面标题、软件名称、版本号和页码属于版式层，不计入 50 行代码正文。代码正文保持原字符，不通过复制、拆行、拼接或生成代码补足页数。

### 4.3 代码页版式

- A4 纵向；
- 生成字号 8.15pt，最终渲染字号不得低于 8pt；
- 单页正文至少 50 行；
- 正文无行号；
- 最长打印列按 100 列控制，超长原始行只允许 CSS 视觉换行，不产生新的有效代码行；
- 页眉显示软件名称与版本，页脚显示当前页码/60。

## 5. 软件说明书设计

### 5.1 内容来源

说明书内容必须来自入选文件中的页面标题、表单字段、按钮、路由、API、状态值、错误分支和数据展示逻辑。生成前先形成题目事实目录，记录每个事实的仓库和文件路径。没有代码或既有文档证据的功能不写入说明书。

三个题目的功能边界分别为：

- 渠道推广与身份核验：渠道人员注册、推广关系、身份核验、学生/就业信息验证、确认单和跨端验证页面。
- 移动端多角色协同：移动工作台、业务订单、履约轨迹、经营统计、收益明细和提现协同。
- 电子协议展示与合规授权：协议路由、协议展示、授权告知、敏感信息提示、服务地址确认、隐私政策和用户协议。

电子协议题目不写“完成电子签章”“合同后台管理”或“签署回调”，因为本题不使用 backend 代码。

### 5.2 统一章节

每套 `02-软件说明书.md` 使用以下结构，并根据实际题目展开：

1. 软件概述
2. 适用范围与业务边界
3. 用户角色与权限
4. 运行环境与访问方式
5. 页面导航与基础操作
6. 核心功能操作
7. 数据输入、处理与输出
8. 状态流转与结果核验
9. 异常提示与恢复操作
10. 权限、安全与隐私注意事项
11. 常见问题与故障排查
12. 补充操作提示

《软件的主要功能》正文必须为 500 至 1,300 个中文字符。说明书按打印行分页为恰好 60 页，每页至少 30 个非空正文行。所有段落必须具体、分级编号且内容不同；禁止循环模板、同义改写补页和脱离系统的通用说明。

### 5.3 文档页版式

- A4 纵向；
- 生成字号 10.15pt，最终渲染字号不得低于 10pt；
- 每页至少 30 个非空正文行；
- 正文无连续行号，页脚页码允许保留；
- 页眉显示软件名称与版本；
- 标题层级、段落间距和表格样式在三套材料中保持一致。

## 6. 其他申报文件设计

### 6.1 软件著作权登记信息表

记录软件全称、简称建议、版本号、软件分类、开发方式、建议完成日期、发表状态、开发目的、适用行业、主要功能、技术特点、代码量、权利范围和主体信息确认状态。无法由代码证明的主体字段明确保留为申请人确认项。

### 6.2 软硬件环境及技术规格

仅根据实际代码和依赖文件列出开发语言、框架、构建工具、客户端形态、运行平台、浏览器或小程序环境、网络条件、存储方式、接口形式和兼容性边界。版本号没有锁定证据时不写精确版本。

### 6.3 代码来源与版本证据

列出全部入选文件、Git 仓库、HEAD 提交、SHA-256、逐行时间范围、首次作品重合结果、题目间去重结果和前后 30 页选择区间，并链接到 `SOURCE_MANIFEST.json`。

### 6.4 申报材料规格与提交核对表

逐项记录：名称一致性、版本一致性、主体信息、60 页、逐页行数、A4、字号、无行号、无第三方代码、无首次作品代码、题目间无重复、说明书主要功能字数、无占位符、PDF 可打开、页眉页脚和人工确认状态。

## 7. 生成组件与数据流

实现新增一个项目材料生成器，职责拆分如下：

1. 清单加载器：读取 CSV，按题目筛选并验证资格字段。
2. Git 对象读取器：按仓库和提交读取源文件并校验 SHA-256。
3. 代码分页器：构建完整代码流，选择连续前后片段并形成 60 页 Markdown。
4. 事实提取器：从 Vue、JavaScript 和 TypeScript 文件提取路由、表单、标签、API 和状态证据。
5. 说明书构建器：以人工核实的题目专用内容源形成 60 页 Markdown，不自动编造缺失事实。
6. 规格文件构建器：生成登记信息、环境规格、来源证据和核对表。
7. 材料审计器：验证 Markdown 逻辑页、逐页行数、代码纯度、哈希、唯一分配和禁用标记。
8. PDF 渲染与审计器：复用仓库现有 WeasyPrint/Poppler 流程，验证实际 60 页、A4、字号和视觉布局。

数据流为：

```text
候选代码审计 CSV
  -> 资格与唯一性验证
  -> Git 提交对象读取和哈希复核
  -> 隔离源清单
  -> 程序材料/题目事实目录
  -> 说明书与规格 Markdown
  -> PDF 渲染
  -> 机器审计 + 全页视觉复核
  -> 单套审计报告 + 三套总审计报告
```

## 8. 失败与保护策略

出现以下任一情况时，该套材料不得标记完成：

- 源文件缺失、Git 提交不存在或 SHA-256 不一致；
- 代码不足 3,000 个有效行；
- 代码页不是 60 页或任一页少于 50 行；
- 说明书不是 60 页或任一页少于 30 行；
- 说明书出现事实无法追溯、重复填充、占位符或功能夸大；
- 出现首次作品路径、第三方目录、题目间重复哈希或未提交文件；
- PDF 不是 A4、字号低于下限、出现裁切、重叠、乱码或页眉页脚错误；
- 登记信息中未确认字段被当作已确认内容输出。

失败只允许通过补充真实说明、缩小不实描述、调整版式或重新选择合格代码解决，禁止生成、复制、扩写、拼接或改写源代码补量。

## 9. 测试与验收证据

### 9.1 自动测试

- 清单只加载 58 个已分配文件、总计 13,140 个有效行；
- 三题分别保持 21/4,838、12/3,968、25/4,334 的审计基线；
- 所有入选哈希唯一，资格字段全部通过；
- 三套程序 Markdown 各 60 页、每页恰好 50 个代码行；
- 三套说明书 Markdown 各 60 页、每页至少 30 个正文行；
- 代码正文逐行可在源 Git 对象中回溯；
- 三套规格文件齐全且软件名称、版本号一致；
- 最终六份 PDF 各 60 页、A4、字号和逐页行数达标。

### 9.2 视觉验收

使用 Poppler 将六份 PDF 全部渲染为 PNG，检查所有页面接触表，并重点查看第 1、30、31、60 页。验收要求为：无裁切、无重叠、无乱码、代码可读、标题层级稳定、页码连续、前后 30 页切换清晰。

### 9.3 状态口径

只有当单套 Markdown、PDF、机器审计和全页视觉检查全部通过，才能称该套“材料生成并复核完成”。本地提交不等于已经提交登记、受理或登记成功。
