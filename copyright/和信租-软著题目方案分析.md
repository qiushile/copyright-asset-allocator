## 一、审计规则

本次题目不是按“仓库首次提交日期”粗略判断，而是对每个候选文件在当前 HEAD 执行 Git blame：

1. 当前每一条非空行的 `author-time` 都必须不早于 2025-08-02；只达到 50% 的文件不进入候选清单。
2. 与首次作品完成日快照内容哈希完全相同的文件排除。
3. 与首次作品相同相对路径、去空白后相似度不低于 80% 的文件排除。
4. 多个新题目之间按内容哈希唯一分配；相同内容只能进入一个题目。
5. 第三方依赖、构建产物、锁文件和未提交工作树改动排除。

严格审计得到 64 个题目范围内文件，其中 58 个文件、13,140 个有效行通过并完成唯一分配。

## 四、实施顺序

建议按以下顺序继续：

1. 先做“渠道推广与身份核验管理系统”，代码边界最清楚、余量最大。
2. 再做“移动端多角色业务协同管理系统”，严格按候选清单取码，不补入共享框架。
3. 最后评估“电子协议展示与合规授权管理系统”的代码页纯度；审计不过则不申报，不拼接 backend 代码补量。

每个题目的下一道真实验收门是：锁定 HEAD → 生成独立工作区 → 路径/哈希/相似代码复核 → Markdown 程序材料 → PDF 60 页渲染复核 → 独立用户说明书。当前尚未执行材料生成和最终 PDF 审计。
